1. Playwright Locators & Web-First Assertions ⏱ ~20 min

🚩 Why it matters: Traditional Selenium sleep timers cause slow, flaky automation. Playwright locators auto-wait for elements to be visible, enabled, and stable before performing actions.

Locators are at the core of Playwright auto-waiting. Unlike Selenium `findElement()`, a Playwright `locator` does not immediately query the DOM — it is an immutable description of how to find elements when an action (like `.click()`) or assertion (like `expect().toBeVisible()`) is executed.

Complete Example
import { test, expect } from '@playwright/test';

test('User authentication flow', async ({ page }) => {
  // Navigate to login page
  await page.goto('http://localhost:3000/login');

  // Locate input fields via accessibility role & label
  const usernameInput = page.getByLabel('Username');
  const passwordInput = page.getByLabel('Password');
  const submitButton = page.getByRole('button', { name: 'Sign In' });

  // Auto-waiting click and type actions
  await usernameInput.fill('alice_admin');
  await passwordInput.fill('SecurePass123!');
  await submitButton.click();

  // Web-first polling assertion
  const welcomeBanner = page.getByTestId('welcome-banner');
  await expect(welcomeBanner).toBeVisible({ timeout: 5000 });
  await expect(welcomeBanner).toContainText('Welcome back, alice_admin');
});
page.getByLabel('Username') — Recommended locator strategy matching accessible form label text.
page.getByRole('button', { name: 'Sign In' }) — Matches accessibility role and visible text, ensuring button is accessible to screen readers.
await expect(welcomeBanner).toBeVisible() — Web-first assertion that automatically polls DOM until visible or timeout is reached.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Using `await page.waitForTimeout(5000)` hardcoded sleep calls in test suites.

Fix: Use web-first assertions like `await expect(locator).toBeVisible()` which retry automatically.

🔮 Predict the Output / Behavior

Scenario: What happens if the Sign In button is disabled when page.click() is called?

Answer: Playwright auto-waits until the button becomes enabled. If it remains disabled after timeout (30s), it throws an Actionability Error.

🧪 Knowledge Check

Question: Why are web-first assertions superior to standard Jest expect(await element.isVisible()).toBe(true)?

✅ Answer: Web-first assertions automatically retry polling the DOM for state changes, eliminating timing race conditions.

Rationale: expect(locator).toBeVisible() retries up to timeout, whereas expect(boolean).toBe(true) evaluates once instantly.

2. Page Object Model (POM) Design Pattern ⏱ ~25 min

🚩 Why it matters: Hardcoding locators inside test files leads to massive code duplication when UI elements change. POM encapsulates page locators and actions into reusable class objects.

The Page Object Model (POM) creates an abstraction layer between test scenarios and page structure. Test files focus on business logic while Page Object classes handle DOM locators and page interactions.

Complete Example
// pages/LoginPage.ts
import { Page, Locator, expect } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly usernameInput: Locator;
  readonly passwordInput: Locator;
  readonly submitButton: Locator;

  constructor(page: Page) {
    this.page = page;
    this.usernameInput = page.getByLabel('Username');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton = page.getByRole('button', { name: 'Sign In' });
  }

  async goto() {
    await this.page.goto('/login');
  }

  async login(user: string, pass: string) {
    await this.usernameInput.fill(user);
    await this.passwordInput.fill(pass);
    await this.submitButton.click();
  }
}
readonly page: Page — Stores Playwright Page instance inside class.
this.usernameInput = page.getByLabel(...) — Initializes locators lazily inside constructor.
async login(user, pass) — Reusable business action encapsulating form interaction.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Calling `await page.locator()` inside constructor instead of assigning locator reference.

Fix: Assign `page.locator()` directly to property without `await` because locators are lazy references.

🔮 Predict the Output / Behavior

Scenario: If the ID of the username field changes in HTML, how many files do you edit in a POM architecture?

Answer: Only 1 file (the LoginPage class), preserving all 50+ test files without edits.

🧪 Knowledge Check

Question: What is the main benefit of Page Object Model in test automation pipelines?

✅ Answer: Maintainability, reusability, and elimination of locator duplication across test suites.

Rationale: POM separates test intent from DOM implementation details.
