1. Page Object Model (POM) Design Pattern in TypeScript vs JavaScript ⏱ ~35 min

🚩 Why it matters: Hardcoding locators inside 50 different test files creates a maintenance nightmare when a developer changes an input ID or button label. Page Object Model encapsulates locators and actions into clean, reusable class files.

💡 Explain Like I'm 5 (ELI5) / Beginner Analogy:

Think of Page Object Model like organizing tools in a labeled toolbox:\n• Without POM = Strewing 50 screwdrivers and hammers across your garage floor (locators scattered everywhere). If a hammer breaks, you have to search 50 rooms to find it!\n• With POM = Putting all plumbing tools in a drawer labeled "PlumbingPage.ts" and electrical tools in "ElectricalPage.ts". If the plumbing wrench changes, you open 1 drawer, swap 1 wrench, and all your jobs work instantly!

📖 Deep Conceptual Breakdown:

The Page Object Model (POM) creates an abstraction layer between test scenarios and page structure:\n\n1. Page Object Class: A class file (e.g. `LoginPage.ts`) representing a specific web page or UI component.\n2. Locators as Class Properties: Define locators as `readonly` class properties inside constructor (e.g. `this.usernameInput = page.getByLabel("Username")`). Locators are lazy references so they do not query DOM until an action is called.\n3. Reusable Action Methods: High-level business actions like `await loginPage.login("alice", "pass123")` encapsulate fill & click steps.\n4. Test Spec Files: Clean test files (`login.spec.ts`) that read like English business requirements!

Complete Example
// pages/LoginPage.ts (TypeScript Version)
import { Page, Locator, expect } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly usernameInput: Locator;
  readonly passwordInput: Locator;
  readonly submitButton: Locator;
  readonly errorMessage: Locator;

  constructor(page: Page) {
    this.page = page;
    // Locators initialized lazily - NO await required here!
    this.usernameInput = page.getByLabel('Username');
    this.passwordInput = page.getByLabel('Password');
    this.submitButton = page.getByRole('button', { name: 'Sign In' });
    this.errorMessage = page.getByRole('alert');
  }

  async goto() {
    await this.page.goto('/login');
  }

  async login(user: string, pass: string) {
    await this.usernameInput.fill(user);
    await this.passwordInput.fill(pass);
    await this.submitButton.click();
  }

  async assertErrorMessage(expectedText: string) {
    await expect(this.errorMessage).toBeVisible();
    await expect(this.errorMessage).toContainText(expectedText);
  }
}

/* Equivalent JavaScript (JS) Version Note:
In plain JS, simply remove type declarations like 'readonly page: Page' 
and parameter types like 'user: string'. The rest of the constructor and 
methods remain 100% identical! */
readonly usernameInput: Locator — TypeScript property declaration enforcing Locator type for VS Code auto-complete.
this.usernameInput = page.getByLabel(...) — Lazy locator definition inside constructor. Does NOT perform DOM lookup until action is executed.
async login(user, pass) — Reusable business action encapsulating form interaction.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Putting `await` inside the Page Object constructor (e.g. `this.usernameInput = await page.getByLabel(...)`).

Fix: Never use `await` inside constructors! Locators are lazy references; `await` is only used when calling actions like `.click()` or `.fill()`.

🔮 Predict the Output / Behavior

Scenario: Why are locators defined as class properties in Page Objects without `await`?

Answer: Because locators are lazy references that describe how to find an element, only executing DOM queries when actions or assertions are called.

🧪 Knowledge Check

Question: What is the primary advantage of using Page Object Model in Playwright suites?

✅ Answer: Single point of maintenance for UI element locators across 100+ test files.

Rationale: If a button label changes, you update 1 line in the Page Object class instead of editing 100 test files.

2. Custom Test Fixtures (base.extend) & Global Setup ⏱ ~35 min

🚩 Why it matters: Instantiating `const loginPage = new LoginPage(page)` inside every test file creates repetitive boilerplate. Playwright custom fixtures inject page objects into test parameters automatically.

💡 Explain Like I'm 5 (ELI5) / Beginner Analogy:

Think of Custom Test Fixtures like a hotel room service breakfast:\n• Without Fixtures = Waking up, walking to the grocery store, buying eggs, cooking them, and washing the pan before eating (doing setup boilerplate in every test).\n• With Custom Fixtures = Placing an order tag on your door before sleep (`test.extend`). When you open your eyes, a hot breakfast is delivered directly to your bed ready to eat (`({ loginPage, dashboardPage }) => { ... }`)!

📖 Deep Conceptual Breakdown:

Playwright built-in fixture system (`test.extend`) allows you to extend the base test runner with custom fixtures.\n\nA fixture is an isolated environment setup/teardown handler. When you define a fixture for `loginPage`, Playwright automatically instantiates `new LoginPage(page)`, passes it into your test function parameter, and performs teardown cleanup after the test finishes.

Complete Example
// fixtures/test-options.ts
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';
import { DashboardPage } from '../pages/DashboardPage';

// Declare TypeScript types for custom fixtures
export type MyFixtures = {
  loginPage: LoginPage;
  dashboardPage: DashboardPage;
};

// Extend base test runner with custom page object fixtures
export const test = base.extend({
  loginPage: async ({ page }, use) => {
    // 1. Setup: Instantiate Page Object
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    
    // 2. Pass fixture instance into test execution
    await use(loginPage);

    // 3. Teardown: (Runs after test completes, if needed)
  },

  dashboardPage: async ({ page }, use) => {
    const dashboardPage = new DashboardPage(page);
    await use(dashboardPage);
  }
});

export { expect } from '@playwright/test';

// Usage in Test File (Clean & Boilerplate-Free):
// import { test, expect } from './fixtures/test-options';
// test('User login test', async ({ loginPage }) => {
//   await loginPage.login('alice', 'pass123');
// });
base.extend({ ... }) — Extends Playwright base test runner with strongly-typed custom fixtures.
await use(loginPage) — Hands fixture instance over to test function and waits for test completion.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Forgetting to call `await use(fixtureInstance)` inside custom fixture definitions.

Fix: Always call `await use(...)` to pass the fixture payload to the test runner.

🔮 Predict the Output / Behavior

Scenario: How does custom test fixture injection improve test code quality?

Answer: It eliminates manual page object instantiation boilerplate from test files.

🧪 Knowledge Check

Question: What is the role of `await use(...)` in Playwright custom fixture functions?

✅ Answer: It passes the initialized fixture object to the test function and marks the boundary between setup and teardown.

Rationale: Code before `use()` is setup; code after `use()` is teardown.
