Database Essentials — Part 1: Relational Databases & SQL

1. What is a Relational Database & Why Do Testers Care? ⏱ ~15 min

💡 Beginner Explanation: Think of a Relational Database like an Excel workbook. Each "Sheet" is a Table. Each "Row" is a Record (e.g. one user or one order). Each "Column" is a Field (e.g. email, age, password hash).

As a Full Stack Developer or SDET, you cannot rely only on what the UI displays. When a user clicks "Register", the UI might show "Success!", but if the database saved NULL for user_id or failed to hash the password, your app has a critical bug!

Key Concepts Explained:

  • Primary Key (PK): A unique ID (like a Social Security Number or UUID) assigned to every row so no two records are confused.
  • Foreign Key (FK): A column in one table that links directly to the Primary Key of another table (e.g., orders.user_id links to users.id).
  • NULL vs Empty String: NULL means missing/unknown data. "" means a known empty string. In database testing, unexpected NULL values cause 80% of backend crashes!

2. Creating Tables with Constraints (DDL) ⏱ ~20 min

Before inserting data, we define the table structure using Data Definition Language (DDL). Constraints enforce business rules at the database layer so bad data can never be saved.

CREATE TABLE users ( id SERIAL PRIMARY KEY, username VARCHAR(50) NOT NULL UNIQUE, email VARCHAR(255) NOT NULL UNIQUE, role VARCHAR(20) DEFAULT 'customer' CHECK (role IN ('customer', 'admin', 'tester')), created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP );

Line-by-Line Breakdown:

id SERIAL PRIMARY KEY: Automatically assigns an auto-incrementing integer (1, 2, 3...) to every new user as their unique identifier.
username VARCHAR(50) NOT NULL UNIQUE: Stores up to 50 characters. NOT NULL prevents missing usernames. UNIQUE prevents two users from picking the same handle.
role ... CHECK (role IN (...)): Enforces that role MUST be one of 'customer', 'admin', or 'tester'. Any other string triggers an immediate SQL error!
