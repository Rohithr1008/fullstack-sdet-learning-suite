1. Understanding SQL Joins (INNER, LEFT, RIGHT, FULL OUTER) ⏱ ~30 min

🚩 Why it matters: Real-world databases do not store all data in one giant flat table. Data is normalized into separate tables (Users, Orders, Products). SQL Joins allow you to query data across multiple tables in a single query.

💡 Explain Like I'm 5 (ELI5) / Beginner Analogy:

Imagine two lists of people at a party:\n• List A = People who registered online (Users table).\n• List B = People who bought a raffle ticket (Orders table).\n\n• INNER JOIN = Only people who are on BOTH lists (Registered users who ALSO bought a ticket).\n• LEFT JOIN = EVERYONE on List A (Registered users), showing their ticket info if they bought one, or NULL if they did not buy a ticket.\n• FULL OUTER JOIN = EVERYONE from List A and List B combined, filling in NULLs wherever matching data is missing.

📖 Deep Conceptual Breakdown:

In a relational database, tables connect through Foreign Keys. For example, the `orders` table has a `user_id` column that points to `users.id`. When writing an INNER JOIN query, SQL looks for matching pairs where `users.id = orders.user_id`. If a registered user has never placed an order, an INNER JOIN excludes them from the query result. If you use a LEFT JOIN, that user will still appear in the result set, with `orders.id` set to `NULL`.

Complete Example
-- Query: Find all orders and display the customer username and email
SELECT 
  users.id AS user_id,
  users.username,
  orders.id AS order_id,
  orders.total_amount,
  orders.created_at
FROM users
INNER JOIN orders ON users.id = orders.user_id
WHERE orders.status = 'completed';
SELECT users.username, orders.total_amount — Selects specific columns from different tables to build combined result set.
FROM users INNER JOIN orders — Combines rows from users table and orders table.
ON users.id = orders.user_id — The join condition specifying how Primary Key (users.id) connects to Foreign Key (orders.user_id).
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Using INNER JOIN when you want to report on ALL users, including users with zero orders.

Fix: Use LEFT JOIN users LEFT JOIN orders ON users.id = orders.user_id so users with no orders remain in the result set with NULL values.

🔮 Predict the Output / Behavior

Scenario: What does orders.user_id contain for an order placed by user with users.id = 42?

Answer: orders.user_id contains the integer 42 (the Foreign Key linking to Primary Key).

🧪 Knowledge Check

Question: Which SQL Join type returns all rows from the left table even if there are no matches in the right table?

✅ Answer: LEFT JOIN (or LEFT OUTER JOIN)

Rationale: LEFT JOIN preserves all rows from the primary left table.

2. SQL Aggregations & Grouping (COUNT, SUM, AVG, GROUP BY, HAVING) ⏱ ~25 min

🚩 Why it matters: Backend analytics, revenue reports, and automated data audits rely on SQL aggregate functions to summarize thousands of database rows.

💡 Explain Like I'm 5 (ELI5) / Beginner Analogy:

Imagine a school teacher calculating grade statistics for a class:\n• COUNT() = Counting the total number of students in the room.\n• SUM() = Adding up all test scores together.\n• AVG() = Calculating the average test score.\n• GROUP BY = Grouping students by their grade level (Freshmen, Sophomores, Juniors, Seniors) before calculating the average for each group!\n• HAVING = Filtering the grouped results (e.g. "Only show grade levels where average score > 85").

📖 Deep Conceptual Breakdown:

SQL aggregate functions operate on sets of rows to return a single summary value. When using aggregate functions alongside non-aggregated columns in a SELECT statement, you MUST include a `GROUP BY` clause listing all non-aggregated columns. Note: `WHERE` filters rows BEFORE grouping occurs, whereas `HAVING` filters aggregated summaries AFTER grouping occurs!

Complete Example
-- Query: Total revenue and total order count per user for completed orders
SELECT 
  users.username,
  COUNT(orders.id) AS total_orders,
  SUM(orders.total_amount) AS total_spent,
  AVG(orders.total_amount) AS avg_order_value
FROM users
INNER JOIN orders ON users.id = orders.user_id
WHERE orders.status = 'completed'
GROUP BY users.id, users.username
HAVING SUM(orders.total_amount) > 100.00
ORDER BY total_spent DESC;
COUNT(orders.id) AS total_orders — Counts total number of non-null order IDs for each grouped user.
GROUP BY users.id, users.username — Mandatory clause grouping aggregated metrics by unique user.
HAVING SUM(orders.total_amount) > 100.00 — Filters grouped results to only show high-value customers who spent > $100.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Trying to use WHERE SUM(orders.total_amount) > 100 instead of HAVING.

Fix: Use WHERE for raw row filtering before grouping; use HAVING for aggregate functions after GROUP BY.

🔮 Predict the Output / Behavior

Scenario: What happens if you run SELECT role, COUNT(*) FROM users without a GROUP BY role clause?

Answer: SQL throws an error: "column users.role must appear in the GROUP BY clause or be used in an aggregate function".

🧪 Knowledge Check

Question: Which SQL clause is used to filter aggregated summary data AFTER GROUP BY has executed?

✅ Answer: HAVING

Rationale: HAVING filters aggregate calculation results; WHERE filters raw table rows.
