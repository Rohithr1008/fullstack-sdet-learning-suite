1. REST Architecture & Anatomy of HTTP Request/Response ⏱ ~20 min

🚩 Why it matters: Modern web applications are built on decoupled architectures where SPA frontends (React/Vue) communicate with backend APIs via HTTP. Understanding status codes, headers, and verbs is essential for SDET API automation.

REST (Representational State Transfer) is an architectural style for designing networked applications. Clients send HTTP Requests containing a URL, HTTP Method (GET, POST, PUT, DELETE, PATCH), Request Headers (Content-Type, Authorization), and an optional Request Body (JSON payload). Servers process the request and return an HTTP Response containing a Status Code (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 500 Internal Error), Response Headers, and Response Body.

Complete Example
// HTTP Request Format:
// POST /api/v1/orders HTTP/1.1
// Host: api.example.com
// Authorization: Bearer eyJhbGciOiJIUzI1Ni...
// Content-Type: application/json

{
  "cartId": 9821,
  "items": [
    { "productId": 401, "quantity": 2, "price": 49.99 }
  ],
  "paymentMethod": "credit_card"
}

// HTTP Response Format:
// HTTP/1.1 201 Created
// Content-Type: application/json
// Location: /api/v1/orders/10542

{
  "orderId": 10542,
  "status": "confirmed",
  "totalAmount": 99.98,
  "createdAt": "2026-09-04T00:39:00Z"
}
POST /api/v1/orders — HTTP Verb POST requests creation of a new order resource at the specified endpoint URL.
Authorization: Bearer — Authentication header passing JWT access token to authorize request.
HTTP/1.1 201 Created — 201 Created status code explicitly confirms new resource was written to database.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Using GET requests to modify or delete data on the server.

Fix: Follow REST standards: GET must be idempotent and safe (read-only). Use POST for creation, PUT/PATCH for updates, DELETE for removals.

🔮 Predict the Output / Behavior

Scenario: What status code should a server return if an API request sends invalid JSON syntactically?

Answer: HTTP 400 Bad Request (Malformed syntax error).

🧪 Knowledge Check

Question: What is the main difference between PUT and PATCH HTTP methods?

✅ Answer: PUT replaces the ENTIRE resource representation, whereas PATCH applies PARTIAL modifications to existing fields.

Rationale: PUT requires passing all fields; PATCH only requires passing fields being updated.

2. JSON Schema Validation & Contract Testing ⏱ ~25 min

🚩 Why it matters: Asserting individual fields like `expect(body.id).toBeDefined()` misses structural breaking changes (e.g. backend developer changing integer `id` to string `uuid`). JSON Schema validates entire structural data contracts.

JSON Schema is a declarative specification for defining the shape, data types, required fields, and validation constraints of JSON objects. In API test automation, tools like Ajv (Another JSON Schema Validator) compare live backend API response payloads against strict JSON Schemas.

Complete Example
import Ajv from 'ajv';
import { test, expect } from '@playwright/test';

// Define strict JSON Schema for User Profile endpoint
const userProfileSchema = {
  type: 'object',
  required: ['id', 'username', 'email', 'roles'],
  properties: {
    id: { type: 'integer', minimum: 1 },
    username: { type: 'string', minLength: 3 },
    email: { type: 'string', format: 'email' },
    roles: {
      type: 'array',
      items: { type: 'string' },
      minItems: 1
    }
  },
  additionalProperties: false // Block unexpected fields
};

test('Validate GET /api/user/1 matches JSON Schema Contract', async ({ request }) => {
  const response = await request.get('/api/user/1');
  const data = await response.json();

  const ajv = new Ajv();
  const validate = ajv.compile(userProfileSchema);
  const valid = validate(data);

  if (!valid) {
    console.error('Schema Errors:', validate.errors);
  }

  expect(valid).toBe(true);
});
required: ['id', 'username', 'email', 'roles'] — Specifies mandatory fields that MUST exist in JSON response.
additionalProperties: false — Strict contract enforcement blocking undocumented API fields from slipping through.
ajv.compile(userProfileSchema) — Compiles JSON Schema into fast validation function.
🐞 Spot the Bug / Edge Case in this topic

Common Pitfall: Writing contract tests without `required` property arrays in JSON Schema.

Fix: Always specify `required: [...]` array so missing keys fail the validation run.

🔮 Predict the Output / Behavior

Scenario: What happens if the API returns `{ id: 1, username: "alice", email: "a@a.com", roles: ["admin"], extraField: true }` when additionalProperties is false?

Answer: Validation fails with error: "must NOT have additional properties".

🧪 Knowledge Check

Question: Why is JSON Schema validation crucial for microservice integration testing?

✅ Answer: It detects contract-breaking changes between frontend and backend teams before deployment to production.

Rationale: Contract tests fail build pipelines immediately when schema types or key names change.
